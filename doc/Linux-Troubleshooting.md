# Linux troubleshooting (Wayland / NVIDIA)

The AppImage launcher (`AppRun`, generated by
`src/platform/unix/BuildLinuxImage.sh.in`) applies the workarounds below
automatically. Set the corresponding environment variable yourself to override
any of them. If you are running a build that predates them, export the
variables manually or put them in the `Exec=` line of your `.desktop` file:

```
Exec=env GDK_BACKEND=x11 __GLX_VENDOR_LIBRARY_NAME=mesa /path/to/CrealityPrint.AppImage %F
```

## Popups never appear on Wayland (KDE Plasma, GNOME)

**Symptom:** the app runs, but transient popups such as the sidebar filament
selector (`FilamentPopPanel`, a `wxPopupTransientWindow`) never show up.

**Cause:** wxGTK popup windows do not work under native GTK-Wayland.

**Workaround:** run through XWayland — `GDK_BACKEND=x11`. The launcher sets
this whenever `WAYLAND_DISPLAY` is present and `GDK_BACKEND` is unset. This is
the same workaround OrcaSlicer documents.

## Crash on launch with a GLX `BadValue` error on hybrid Intel/AMD + NVIDIA laptops

**Symptom:** the window flashes and the process exits with status 1. Run from a
terminal you see:

```
WARNING: Disabled hardware acceleration because GTK failed to initialize GL: Unable to create a GL context.
Gdk-WARNING: The program 'CrealityPrint' received an X Window System error.
The error was 'BadValue (integer parameter out of range for operation)'.
  (Details: serial 557 error_code 2 request_code 149 (GLX) minor_code 3)
```

`glxinfo` works fine and reports the integrated GPU.

**Cause:** the proprietary NVIDIA GLVND vendor library (`libGLX_nvidia.so.0`)
is installed, but the display is driven by the integrated GPU. Under XWayland
there is no `GLX_EXT_libglvnd` server hint, so libglvnd may hand
`glXCreateContext` to the NVIDIA vendor, which fails (most obviously when the
dGPU has no usable userspace driver — `nvidia-smi` reports
`Unable to determine the device handle`).

**Workaround:** force the Mesa vendor — `__GLX_VENDOR_LIBRARY_NAME=mesa`. The
launcher sets this when `libGLX_nvidia.so.0` exists, the boot VGA device
(`/sys/class/drm/card*/device/boot_vga`) is **not** NVIDIA (vendor `0x10de`),
and the variable is unset. Desktops whose primary GPU is NVIDIA are untouched,
and PRIME render-offload users who set `__GLX_VENDOR_LIBRARY_NAME=nvidia`
themselves keep their setting.

## GPU hang / black "Not Responding" window right after slicing (Intel iGPU, Mesa 26.0.x)

**Symptom:** slicing finishes, then 7–8 s later the window goes black and the
title shows "(Not Responding)". The process stays alive. `journalctl -k` shows

```
i915 0000:00:02.0: [drm] CrealityPrint[<pid>] context reset due to GPU hang
```

and a core backtrace of the main thread ends in
`GLCanvas3D::reload_scene → glXMakeCurrent → driUnbindContext → iris`.
Reproduced on a Raptor Lake-U iGPU (8086:a7ac) with Mesa 26.0.8 on every
slice, even a single 950-triangle object.

**Cause:** the first draw of the G-code toolpath preview never completes on
the Intel driver when colour-compression (CCS) surfaces are in use; i915's
hang-checker then resets the context and iris deadlocks on the way out.

**Workaround:** disable CCS for the app — `INTEL_DEBUG=noccs`. The launcher
sets this automatically when an Intel GPU (vendor `0x8086`) is present and
`INTEL_DEBUG` is unset (set `INTEL_DEBUG=` to an empty value to opt out).
Verified with
a scripted repro: `noccs` alone prevents the hang with GPU acceleration kept;
`nohiz`, `LIBGL_DRI3_DISABLE=1`, the GL 2.1 shader path and
`gcode_preview_lite_mode` do not help. `LIBGL_ALWAYS_SOFTWARE=1` (llvmpipe)
also works, at the cost of CPU rendering.

```
Exec=env GDK_BACKEND=x11 __GLX_VENDOR_LIBRARY_NAME=mesa INTEL_DEBUG=noccs /path/to/CrealityPrint.AppImage %F
```

## Cosmetic noise you can ignore

- `Gtk-CRITICAL ... gtk_widget_set_size_request: assertion 'width >= -1' failed`
- `libEGL warning: pci id for fd N: 10de:xxxx, driver (null)` /
  `egl: failed to create dri2 screen` — Mesa enumerating an NVIDIA render node
  it has no driver for; rendering falls back to the integrated GPU.

## Installing the AppImage on KDE Plasma

The AppImage's file name embeds the version, so a `.desktop` file pointing at
it breaks on every upgrade. Either keep a stable symlink
(`~/Applications/CrealityPrint.AppImage -> CrealityPrint-V<ver>-x86_64-Release.AppImage`)
and point `Exec=` at that, or edit `Exec=` after each download and run
`kbuildsycoca6 --noincremental` so the menu picks up the change.
